# چت + میکروفون + Lobby ظرفیت‌محور

*نوشته‌ی لیلا (BA)* — پاسخ به یه تصمیم مهم PO: روم دیگه فقط «چت‌روم با متن» نیست؛ صدا هم داره، و بازی تا پر نشدن ظرفیت شروع نمی‌شه.

## ۱. تغییر قانون Room (اصلاحیه روی سند ۰۵)

قانون قدیم: «هر وقت اعضا `>= MinPlayers` بود، Host می‌تونه Start بزنه.»
**قانون جدید:** Room هنگام ساخت یک `Capacity` مشخص می‌گیره (مثلاً ۸ نفر). Start **غیرفعاله** تا زمانی که `Members.Count == Capacity`. Host نمی‌تونه زودتر شروع کنه — این یه تصمیم عمدیه تا نقش‌ها بر اساس تعداد از پیش تعیین‌شده متعادل بمونن (نسبت مافیا:شهر با تعداد نفرات تغییر می‌کنه، شروع زودهنگام این تعادل رو به‌هم می‌زنه).

| فیلد جدید Room | مقدار |
|---|---|
| `Capacity` | عدد ثابت که Host موقع ساخت روم انتخاب می‌کنه (۶ تا ۱۵) |
| `Status` | `WaitingForPlayers` تا `Members.Count == Capacity`، بعدش `ReadyToStart` |

## ۲. کانال‌های ارتباطی (متن + صدا) — قانون مهم‌تر از رأی علنی!

هرکی با کی می‌تونه حرف بزنه/بشنوه، دقیقاً باید با فاز بازی هماهنگ باشه — وگرنه کل مکانیک مخفی‌کاری بازی بی‌معنی می‌شه:

| فاز | چت متنی | صدا |
|---|---|---|
| **Lobby** | یک کانال عمومی، همه‌ی اعضا | یک کانال صوتی عمومی، همه می‌تونن صحبت کنن |
| **Night** | فقط اعضای `SimpleMafia` زنده (کانال خصوصی) | فقط اعضای `SimpleMafia` زنده — بقیه نه می‌شنون نه می‌تونن حرف بزنن |
| **Day** | عمومی، فقط بازیکنان **زنده** می‌تونن پیام بفرستن | عمومی، فقط زنده‌ها میکروفونشون بازه |
| **بعد از حذف** | بازیکن حذف‌شده خودکار می‌ره توی «چت مرده‌ها» — کانال جدا که فقط بین حذف‌شده‌ها مشترکه | همون؛ صدای مرده‌ها به هیچ‌وجه به زنده‌ها نمی‌رسه |

> **مهم‌ترین ریسک:** اگه بازیکن حذف‌شده بتونه توی کانال زنده‌ها حرف بزنه یا بشنوه، می‌تونه از طریق صدای بیرون (دیسکورد جدا، تماس تلفنی) اطلاعات نقش رو به تیمش لو بده و کل بازی بی‌اعتبار بشه. پس این قانون نباید optional باشه — سرور باید موقع حذف بازیکن، فوراً و به‌صورت اجباری کانال صوتی/متنی‌ش رو عوض کنه، نه اینکه به client اعتماد کنه.

## ۳. Aggregate جدید: VoiceChannel (کنار GameSession)

**چرا Aggregate جدا؟** چون WebRTC signaling (کی به کی وصله، کی mute کرده) یه چرخه‌ی عمر متفاوت از قوانین بازی داره و نباید GameSession رو سنگین کنه.

```
VoiceChannel {
  ChannelId, GameSessionId, ChannelType (Public / MafiaPrivate / DeadChat),
  Members: List<VoiceMember { PlayerId, Muted, Speaking }>
}
```

### Command ها
| Command | قانون |
|---|---|
| `JoinVoiceChannel(playerId, channelType)` | فقط سرور تصمیم می‌گیره کدوم بازیکن مجاز به کدوم کانال — client نمی‌تونه channelType دلخواه بخواد |
| `ToggleMute(playerId)` | خود بازیکن می‌تونه خودش رو mute/unmute کنه (کنترل محلی) |
| *(داخلی)* `ForceChannelSwitch(playerId, newChannelType)` | trigger شده از `PlayerEliminated` یا `NightPhaseStarted`/`DayPhaseStarted` — بازیکن رو بدون اجازه‌ی خودش جابه‌جا می‌کنه |

### معماری فنی پیشنهادی (صدا)
با توجه به تحقیق: توپولوژی **Mesh** (هر بازیکن مستقیم به بقیه وصل بشه) برای بیشتر از ۴-۶ نفر باعث فشار زیاد رو آپلود کاربر می‌شه (هرکسی باید هم‌زمان N-1 استریم بفرسته). برای روم‌های ۶ تا ۱۵ نفره، **SFU** (Selective Forwarding Unit) لازمه — سرور استریم صوتی هرکس رو یک‌بار می‌گیره و فقط برای کسایی که باید بشنون forward می‌کنه. پیشنهاد: استفاده از یه SFU آماده (مثل **LiveKit** یا **mediasoup**) به‌جای پیاده‌سازی WebRTC signaling از صفر — این یه تصمیم build-vs-buy درست برای v1 هست.

## ۴. Chat Message Entity (زیرمجموعه‌ی VoiceChannel یا یه Aggregate سبک جدا: `ChatThread`)

```
ChatMessage { MessageId, ThreadType (Lobby/DayPublic/NightMafia/DeadChat), SenderId, Text, SentAtUtc }
```

قانون: `SendChatMessage` دقیقاً همون قانون دسترسی VoiceChannel رو چک می‌کنه — یعنی یک Command، دو اثر (اگه بازیکن مجاز به کانال صوتیه، مجاز به همون چته).
